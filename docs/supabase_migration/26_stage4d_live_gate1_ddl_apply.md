## 3. A scope issue found during verification, caught and corrected before moving on

The migration's sequence-USAGE-grant loop matched on **schema** (`public`/`provenance`/
`research`) rather than the exact 7 sequences the Gate1.5 mandatory scope needs. The live
catalog already had 4 pre-existing sequences in `public` belonging to out-of-scope tables
(`clinic_email_enrichment`, `new_clinic_candidates`, `new_clinic_candidate_evidence`,
`new_clinic_source_records` — the same 4 tables flagged as "out-of-scope, not audited" back in
the independent Gate1.5 verification). The loop granted `clinic_runtime` USAGE on those 4 too.

**Impact assessed before deciding to fix**: `clinic_runtime` was never given any table-level
`INSERT`/`UPDATE`/`DELETE` grant or RLS policy on those 4 tables, so this was never an actual
data-access path — but it violated the "minimal necessary grant only" principle. Corrected
immediately, same session, before any further verification: a second migration,
`stage4d_scope_fix_revoke_out_of_scope_sequence_grants` (version `20261007014334`), revoked
exactly those 4 grants. Verified after: `clinic_runtime` has `USAGE`/`SELECT` on exactly 7
sequences (`clinics_id_seq`, `source_records_id_seq`, `change_history_id_seq`,
`match_reviews_id_seq`, `comdesk_original_rows_id_seq`, `google_maps_results_id_seq`,
`search_usage_id_seq`) — no more, no less.

The tracked file `stage4d_runtime_write_schema.sql` was corrected in the same commit as this
report (explicit 7-sequence list, guarded by an `exists` check, instead of the schema-wide
scan) so a fresh apply elsewhere will not reproduce this. The corrective SQL that was actually
run live is preserved as its own tracked file,
`stage4d_scope_fix_revoke_out_of_scope_sequence_grants.sql`, so Git and the live database stay
consistent — no live-only, unmanaged change exists.
