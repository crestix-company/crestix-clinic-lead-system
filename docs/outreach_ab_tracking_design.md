## 0. 最重要の発見：Gmail送信・追跡は既に別パイプラインで稼働している

当初(本書の前バージョン)は「送信・開封・クリックの追跡は未構築」という前提で設計していたが、**誤りだった**。
実シートを確認したところ、次が判明した。

- 「案件管理」シートには送信日時・下書きThreadID・送信ThreadID・初回開封推定日時・高信頼開封・
  記事クリック有無・初回クリック日時・返信有無・メール経由アポ・アポ日時までの列が**実データ付きで**
  既に存在する。
- 「トラッキングログ」シートには開封/クリックイベントごとに、UserAgent・IPハッシュ・ASN・
  ネットワーク組織・信頼度（`google_proxy`/`human_like`等）・CF-Rayが記録されている。これはボット・
  プロキシ経由の開封を除外するための開封推定ロジックが、**既に実装・運用されている**ことを示す。
- 「集計」シートには、テンプレート番号ごとに送信数・開封推定率・返信率・クリック率・アポ率を出す
  ピボットが既に存在する。

つまり、Gmail下書き作成・送信・開封/クリック追跡・アポ集計は、**このリポジトリとは別のシステム
（おそらくGoogle Apps Script等によるWebhook／自動化。実体コードへのアクセスは今回確認できなかった
― §1参照）で既に本番稼働している。**

**この発見により、設計の前提が変わる。** 本書が解くべき問題は「トラッキングをゼロから作る」ことでは
なく、「PR #67の`generation_batch_id`／`clinic_uuid`／`template_id`／`template_version`を、この
既存パイプラインに**入力として**渡せるようにする（既存の`案件ID`の意味や採番ルールは変更しない）」
ことである。

**未確定・要確認**: PR #67の「メール送付文章」（CSV出力のみ）と、この既存の案件管理パイプラインが
今後どういう関係になるのか（後者にCSVを読み込ませる前段になるのか、両者は無関係に併存するのか、

## 4. ID連携設計（既存`案件ID`体系は変更しない。誤紐づけ・重複送信の防止を優先）

### 4.1 各識別子の役割と粒度

| 識別子 | 所有システム | 粒度 | 発生タイミング |
|---|---|---|---|
| `clinic_uuid` | PR #67（Clinic Master由来） | 1医院 | Clinic Master抽出時 |
| `generation_batch_id` | PR #67 | 1回の一括生成（複数医院を含む） | 「①対象選択」でCSVを生成した瞬間 |
| `template_id` / `template_version` | PR #67 | 1生成結果（医院単位） | 文章生成時 |
| `variant_id`（A/B用） | **未実装**。実装するなら発行元はPR #67側を想定 | 1生成結果（医院単位） | 未実装 |
| 既存`案件ID` | 既存パイプライン（所有者不変） | 1送信試行（医院×タイミング） | 既存「フォーム回答」受付時に既存システムが採番 |
| Gmail Thread ID | 既存パイプライン（Gmail側） | 1メールスレッド | 既存システムがGmail下書きを作成した時点 |

**重要**: `案件ID`は1医院1送信試行ごとに新規発行される、既存システム側の主キーである。PR #67側の
識別子（`clinic_uuid` / `generation_batch_id` / `template_id` / `template_version` / `variant_id`）は、
**いずれも`案件ID`を代替しない。`案件ID`の採番ルール・意味・既存の値は一切変更しない。**

### 4.2 マッピングの考え方

`案件ID`＝1送信試行、`generation_batch_id`＝1バッチ（複数医院を含む）なので、両者は1:1ではない。
**(`generation_batch_id`, `clinic_uuid`) の組が、「このバッチでこの医院に送る予定だった1件」を
一意に表す**。この組が、実際に既存パイプラインに取り込まれて`案件ID`が発行された瞬間に、
その`案件ID`と1:1で結びつく。

マッピングは新しいテーブルを作るのではなく、**既存「案件管理」シートに4列を追加する案**とする
（別シートに分離すると、既存の`案件ID`中心の運用から外れたデータが生まれ、かえって誤紐づけの
リスクが上がるため）。

| 追加列（案） | 内容 |
|---|---|
| `clinic_uuid` | PR #67 CSV由来 |
| `generation_batch_id` | PR #67 CSV由来 |
| `template_id` / `template_version` | PR #67 CSV由来 |
| `variant_id` | 未実装（列のみ予約） |

`Gmail Thread ID`は新規列を追加せず、既存の`下書きThreadID` / `送信ThreadID` / `ThreadID`列を
そのまま正式な参照先として扱う（既存列と重複する列を増やさない）。

### 4.3 受け渡し経路（案、未実装）

既存「フォーム回答」シートの`フォームJSON`は自由形式のJSONであることを確認済み（§2.1）。この
JSONに`clinic_uuid` / `generation_batch_id` / `template_id` / `template_version` / `variant_id`
を追加フィールドとして含め、既存パイプライン側が`案件管理`へ行を作成する際にこれらを4.2の新規列へ
書き写す、という流れを想定する。**ただし既存パイプラインのJSONパース処理・バリデーションの実装を
確認できていないため（§1）、未知のフィールドを追加しても既存処理を壊さないかは未確認・要確認。**

### 4.4 誤紐づけの防止

- 結合キーには**必ず`clinic_uuid`を使い、医院名・メールアドレスは使わない**（医院名は表記ゆれ、
  メールアドレスは代表窓口共有の可能性があり、いずれも一意性を保証できないため）。
- `案件ID`は既存システムが発行するものをそのまま受け取るだけで、PR #67側で`案件ID`を**推測・生成
  しない**（採番ルールが未確認のため、自前採番は衝突・誤発行のリスクがある）。
- Gmail Thread IDは既存システムが送信後に払い出す値であり、PR #67側が事前に知ることはできない
  （結合キーとしては使えない。あくまで事後の参照用）。

### 4.5 重複送信の防止（1医院への複数送信案件は許容した上で）

要件どおり「1医院に複数の送信案件が存在する」こと自体は許容する（例: 別の日の別バッチで再アプローチ
するケース）。一方で**同一バッチ内で同じ医院へ誤って2回取り込まれる**事故は防ぎたい。

- **防止の単位**: `(generation_batch_id, clinic_uuid)` の組をユニークキーとする。
  - PR #67側: `select_targets`は既にバッチ内で`clinic_uuid`の重複を除外済み（既存機能、変更なし）。
    したがって1つの`generation_batch_id`内で同じ`clinic_uuid`が複数行CSVに出ることはない。
  - 既存パイプライン側（未実装・要確認）: フォーム取り込み時に`(generation_batch_id, clinic_uuid)`
    の組が既に`案件管理`に存在するかをチェックし、存在すれば新規`案件ID`を発行せず警告する、という
    ガードを追加する案。これは既存パイプラインの改修が必要なため、別途実装要否を協議する。
- **意図的な再送（別バッチ）との区別**: `generation_batch_id`が異なれば、同じ`clinic_uuid`でも
  正当な別案件として扱う（ブロックしない）。これにより「1医院に複数の送信案件を許容」という要件と
  「同一バッチ内の誤重複を防ぐ」という要件を両立する。

## 5. 期間・IS担当者・テンプレート別の効果測定設計（既存シートをREAD ONLYデータソースとして使う前提）

「集計」シートが、テンプレート番号別の集計という形で**既にほぼ同じことをしている**。これを拡張する案。
**本システム（PR #67）から既存シートへの書き込みは行わない。** 読み取り専用の集計ビュー（既存シート上の
新規ピボット、またはPR #67側からのREAD ONLY API参照）として設計する。

### 5.1 指標定義（開封は推定値／高信頼値を区別する）

| 指標 | 定義 | 既存シートの対応列 |

### 6.12 gcloud標準OAuthクライアントのスコープ制限への対応（カスタムOAuthクライアント方式）

§6.10方式Aで案内した`gcloud auth application-default login`は、**gcloud自身が持つ共有の標準OAuth
クライアント**を使う。Googleの制限ポリシーにより、この標準クライアントでは一部のスコープ（Sheets等）
が制限対象になる場合がある
（参考: https://docs.cloud.google.com/docs/authentication/troubleshoot-adc#access_blocked_when_using_scopes
― ユーザーが提示）。

この場合、**ユーザー自身のGoogle CloudプロジェクトでカスタムOAuthクライアントID（デスクトップアプリ
種別）を作成し、`--client-id-file`で指定する方式**に切り替える。

**PR #75の実装(`google.auth.default()`)は、変更なしでこの方式に対応できることを確認済み。**
`google.auth.default()`はローカルのADC認証情報ファイル（`~/.config/gcloud/application_default_credentials.json`）
を読むだけで、そのファイルが標準クライアント経由で作られたかカスタムクライアント経由で作られたかを
区別しない。実際のスコープ付与は`gcloud auth application-default login --scopes=...`実行時の1回だけ
行われる（`sheets_source.py`内で渡している`scopes=[READONLY_SCOPE]`引数は、ユーザー認証情報
〈authorized_user型〉に対しては効果を持たない。これはGoogle認証ライブラリの既知の仕様で、サービス
アカウント方式の場合にのみ有効に働く）。したがって**コード変更は不要**。

**1. 既存Google Cloudプロジェクトの確認方法**

```bash
# gcloud未ログインの場合はまずログイン
gcloud auth login

# 既存プロジェクトの一覧を確認
gcloud projects list

# 既に使っているプロジェクトがあれば、それを使い続けてよい（新規作成は不要）
export GCP_PROJECT_ID="<既存または選択したプロジェクトID>"
gcloud config set project "$GCP_PROJECT_ID"
```

**2. Google Sheets APIの有効化**

```bash
gcloud services enable sheets.googleapis.com --project="$GCP_PROJECT_ID"

# 有効化されたか確認
gcloud services list --enabled --project="$GCP_PROJECT_ID" | grep sheets
```

**3. Desktop OAuthクライアントIDの作成方法（ブラウザ操作、gcloud CLIに該当コマンドが無いため）**

Cloud ConsoleのUI操作が必要（2026年時点、汎用OAuthクライアントID作成をgcloud CLI単体で行う安定した
コマンドは無いため、Console UIでの作成を案内する）。

1. ブラウザで https://console.cloud.google.com/apis/credentials を開き、対象プロジェクト
   （`$GCP_PROJECT_ID`）を選択する。
2. 初回は「OAuth同意画面」の設定を求められる場合がある。User Type は**「外部」**を選択し、
   公開ステータスは**「テスト」のまま**でよい（社内の少人数利用のため、Googleによるアプリ審査は
   不要）。テストユーザーに、ADCログインで使う自分のGoogleアカウントを追加する。
3. 「認証情報を作成」→「OAuth クライアント ID」を選択。
4. アプリケーションの種類で**「デスクトップ アプリ」**を選択し、名前を入力（例:
   `outreach-sheets-readonly-desktop`）。
5. 作成後に表示される画面、または認証情報一覧から「JSONをダウンロード」する。

**4. ダウンロードした鍵の保管、および`--client-id-file`を使うADC認証手順**

```bash
# ダウンロードしたファイルをリポジトリの外、パーミッション制限した場所に移動する
mkdir -p ~/.config/outreach-dashboard
mv ~/Downloads/client_secret_*.json ~/.config/outreach-dashboard/oauth-client-desktop.json
chmod 600 ~/.config/outreach-dashboard/oauth-client-desktop.json
```

**5. cloud-platformとspreadsheets.readonlyのスコープ設定でADCログイン**

```bash
gcloud auth application-default login \
  --client-id-file="$HOME/.config/outreach-dashboard/oauth-client-desktop.json" \
  --scopes="https://www.googleapis.com/auth/cloud-platform,https://www.googleapis.com/auth/spreadsheets.readonly"

# ADCのクォータ参照先プロジェクトを明示
gcloud auth application-default set-quota-project "$GCP_PROJECT_ID"
```

ブラウザが開き、ログイン・同意を求められる（対象シートに既にアクセス権のあるGoogleアカウントで
ログインする）。「このアプリは確認されていません」という警告が出ることがあるが、自分がOAuth
同意画面のテストユーザーとして登録した本人のアプリなので、「詳細」→「（アプリ名）に移動」で進めてよい。

**6. 認証完了後のREAD ONLY接続検証**

```bash
gcloud auth application-default print-access-token > /dev/null && echo "ADC OK"

export OUTREACH_SHEETS_ID="1fqzCokKT2q5Iv4rMZBg8oSSXmtj2x_vdnw7sJqTbT9s"
pip install google-api-python-client google-auth

python scripts/launch_effect_dashboard.py
```

ブラウザでダッシュボードを開き、「🔒 既存Google Sheetsの実データを表示しています」の表示、および
§6.6の整合性確認パネルで対象テンプレートがすべて「✅」になることを確認する。

**注意（認証情報の非コミット・非ログ出力）**:
- ダウンロードしたOAuthクライアントJSON（`client_secret_*.json`）、ADCトークンファイル
  （`application_default_credentials.json`）は、いずれもリポジトリの外（`~/.config/...`）に置き、

  している）。
- `sheets_source.py`のエラーメッセージには認証情報の値・パスを含めないことを引き続き保証する
  （§6.5の監査で確認済み、変更なし）。
