## 0. 最重要の発見：Gmail送信・追跡は既に別パイプラインで稼働している

当初(本書の前バージョン)は「送信・開封・クリックの追跡は未構築」という前提で設計していたが、**誤りだった**。
実シートを確認したところ、次が判明した。

- 「案件管理」シートには送信日時・下書きThreadID・送信ThreadID・初回開封推定日時・高信頼開封・
  記事クリック有無・初回クリック日時・返信有無・メール経由アポ・アポ日時までの列が**実データ付きで**
  既に存在する。
- 「トラッキングログ」シートには開封/クリックイベントごとに、UserAgent・IPハッシュ・ASN・
  ネットワーク組織・信頼度（`google_proxy`/`human_like`等）・CF-Rayが記録されている。これはボット・
  プロキシ経由の開封を除外するための開封推定ロジックが、**既に実装・運用されている**ことを示す。
- 「集計」シートには、テンプレート番号ごとに送信数・開封推定率・返信率・クリック率・アポ率を出す
  ピボットが既に存在する。

つまり、Gmail下書き作成・送信・開封/クリック追跡・アポ集計は、**このリポジトリとは別のシステム
（おそらくGoogle Apps Script等によるWebhook／自動化。実体コードへのアクセスは今回確認できなかった
― §1参照）で既に本番稼働している。**

**この発見により、設計の前提が変わる。** 本書が解くべき問題は「トラッキングをゼロから作る」ことでは
なく、「PR #67の`generation_batch_id`／`clinic_uuid`／`template_id`／`template_version`を、この
既存パイプラインに**入力として**渡せるようにする（既存の`案件ID`の意味や採番ルールは変更しない）」
ことである。

**未確定・要確認**: PR #67の「メール送付文章」（CSV出力のみ）と、この既存の案件管理パイプラインが
今後どういう関係になるのか（後者にCSVを読み込ませる前段になるのか、両者は無関係に併存するのか、
将来的に統合するのか）は本書では決めていない。これは実装着手前に必ず確認が必要な最上位の論点。

## 4. 結合キーのマッピング設計（案。既存`案件ID`の意味は変更しない）

既存`案件ID`は**そのまま維持**し、新たに次の列を「案件管理」シート（または別の中間マッピングシート）
に追加する案とする。

| 新規列（案） | 値の出所 | 備考 |
|---|---|---|
| `clinic_uuid` | PR #67のCSV出力（既存列） | マイナビ医院ページURLのスラッグ由来、既存の`掲載記事URL`より確実な結合キー |
| `generation_batch_id` | PR #67のCSV出力（既存列） | 1回の一括生成＝1バッチ。1バッチに複数`clinic_uuid`が含まれる |
| `template_id` | PR #67のCSV出力（既存列） | `LISTED_FIXED` / `RECOMMEND_PROVISIONAL` |
| `template_version` | PR #67のCSV出力（既存列） | 現状は両方`v1` |
| `variant_id` | **未実装**（将来のA/B用、今回は列の予約のみ） | §5のA/B設計が確定してから値を入れる |
| `gmail_thread_id` | 既存の`下書きThreadID`/`送信ThreadID`をそのまま参照 | 新規列は不要。既存列名をそのまま正式名称として扱う案 |

**粒度の違いへの対応**: `案件ID`＝1医院への1送信試行、`generation_batch_id`＝1バッチ（複数医院）
なので、両者は1:1ではない。**(`generation_batch_id`, `clinic_uuid`) の組**が、既存の`案件ID`
1件に相当する（想定）。つまり「このバッチのこの医院」＝「あの案件ID」という対応を、案件が実際に
送信パイプラインに入った時点で記録する必要がある。

**想定される受け渡し方法（案、未実装）**: PR #67のCSV（または将来のAPI）を既存の「フォーム回答」の
入力経路に流し込む際、`フォームJSON`に`clinic_uuid` / `generation_batch_id` / `template_id` /
`template_version`を追加フィールドとして含める。既存パイプライン側（GAS等）がこのJSONから「案件管理」
シートへ新規列として書き写す、という流れを想定するが、**既存パイプラインのコードを確認できていない
ため、実際にこの改修が可能か・妥当かは別途、既存パイプラインの開発者に確認が必要。**

## 5. 期間指定集計・A/Bテスト比較の仕様（案）

「集計」シートが、テンプレート番号別の集計という形で**既にほぼ同じことをしている**。これを拡張する案。

### 5.1 指標定義（開封は推定値／高信頼値を区別する）

| 指標 | 定義 | 既存シートの対応列 |
|---|---|---|
| 送信数 | 期間内に`送信有無`＝送信済みの件数 | 案件管理.送信有無, 送信日時 |
| 返信数 | 期間内に`返信有無`＝ありの件数 | 案件管理.返信有無, 初回返信日時 |
| 開封推定数（広義・推定値） | `開封推定レベル`が「可能性あり」以上（ボット／プロキシ経由を含む可能性がある緩い基準） | 案件管理.開封推定レベル |
| 開封数（高信頼値） | `高信頼開封`＝ありの件数（トラッキングログの`信頼度`=highかつ`分類`=human_like相当で判定されたもの） | 案件管理.高信頼開封, トラッキングログ.信頼度/分類 |
| 記事クリック数 | `記事クリック有無`＝ありの件数（広義）、または`高信頼クリック数`（厳格） | 案件管理.記事クリック有無, 高信頼クリック数 |
| アポ数 | `メール経由アポ`＝ありの件数、または`アポ日時`が入っている件数 | 案件管理.メール経由アポ, アポ日時 |

**開封推定数と高信頼開封数は必ず別々に出す**（広義の推定値をそのままアポ率等の分母・分子に使うと、
ボット開封によって水増しされた指標になるため）。

### 5.2 期間指定集計（案）

- フィルタ基準列: `送信日時`（既存の「集計」シートは全期間集計のみなので、期間フィルタを追加する形）
- 集計粒度（将来的に選択可能にする案）: 全体 / `generation_batch_id`単位 / `template_id`+
  `template_version`単位 / 既存`テンプレート`番号単位 / `variant_id`単位（A/B実装後）
- 出力指標: 送信数・返信数・開封推定数・高信頼開封数・記事クリック数・アポ数、および
  返信率・開封推定率・高信頼開封率・クリック率・アポ率（いずれも分母は送信数）

### 5.3 A/Bテスト比較の仕様（案）

- 比較軸: `variant_id`（未実装）。実装するまでの代替として、既存`テンプレート`番号を暫定的な比較軸に
  使うことも可能だが、**既存`テンプレート`番号の意味（何を変えた文面なのか）を確認してからでないと、
  何と何を比較しているのか誤認するリスクがある（未確認・要ヒアリング）**。
- 比較する指標: §5.1の各指標の群間比較（例: `variant_id=A` vs `variant_id=B`の開封率・返信率・
  アポ率）。
- 統計的有意性の検定（例: カイ二乗検定）を入れるかどうかは今回は未決定（要件次第で別途設計）。
